## 2024-12-16 - Prevent PHP Object Injection in Pluggable Queues via Strict Deserialization
**Vulnerability:** Pluggable queue systems (such as `database`, `redis`, `beanstalkd`, `sync`) deserialize jobs stored as payload strings. Because PHP's `unserialize()` was called without any restriction on `allowed_classes`, any malicious payload injected into the queues could trigger PHP Object Injection (POP gadget chain), allowing arbitrary code execution or arbitrary file deletion on the worker server.
**Learning:** In a decentralized queue or RPC architecture where jobs or messages are serialized and passed around, trusting the content of raw payloads for unrestricted `unserialize()` is extremely risky. Since every job payload specifies its expected `job` class name, we can strictly restrict `unserialize()`'s `allowed_classes` option to exactly the expected class name.
**Prevention:** Never use unrestricted `unserialize($data)`. Always pass a strict whitelist of classes using `['allowed_classes' => [$jobClass]]` or `['allowed_classes' => false]` to prevent unexpected object instantiation and magic methods from triggering.

## 2025-01-14 - Prevent Username/Email Enumeration via Login Timing Side-Channels and CPU DoS on Large Passwords
**Vulnerability:** The authentication system verified passwords using `password_verify` only if the user was found in the database. When the user was not found, the function was bypassed entirely. Because BCrypt password verification is computationally expensive, this timing difference allowed attackers to scan and enumerate valid emails. Furthermore, extremely long password inputs were not capped, introducing a CPU exhaustion Denial-of-Service (DoS) vector during password hashing.
**Learning:** Even if queries use safe prepared statements, execution flow differences between user-exist and user-absent branches can leak secret states via high-resolution timing measurements. In addition, security-related CPU-heavy operations must always be protected with maximum size boundaries to avoid denial of service.
**Prevention:** Always verify a pre-computed dummy BCrypt hash when the query result is empty, ensuring both flows run the hashing function. Enforce a strict length limit (such as 255 characters) on all user password inputs before invoking hashing or verification APIs.

## 2025-02-15 - Secure Reverse-Proxy HTTPS Detection and HSTS Mitigation against Header Spoofing
**Vulnerability:** Blindly trusting client-supplied headers like `X-Forwarded-Proto` to detect secure (HTTPS) requests opens up protocol header spoofing vulnerabilities. If the application is deployed behind a misconfigured proxy, attackers can spoof HTTPS state, bypassing secure session cookie flags or triggering unexpected behaviors.
**Learning:** Request scheme and secure session handling must only trust proxy-forwarded protocols if the upstream proxy itself is explicitly trusted (via defined trusted proxy IPs or wildcards). Centralizing this detection ensures that security middleware (like HSTS) and cookies (session/CSRF) remain securely bound.
**Prevention:** Implement a Trusted Proxies check (`TRUST_PROXIES` whitelist) when detecting HTTPS state from headers, and only apply HSTS and Secure cookie flags on verified secure channels.

## 2025-03-03 - Open Redirect Mitigation in Redirection and Auth Scaffolds via Safe Local Redirect Validation
**Vulnerability:** Redirection to user-controlled or session-flashed values (such as `'intended'` URL on login or password confirmation) introduced Open Redirect vulnerabilities. Attackers could trick users into clicking links that authenticated them and subsequently redirected them to arbitrary external phishing sites.
**Learning:** Redirection targets supplied from request inputs or flashed variables should never be trusted blindly. Safe redirects should either be strictly local (relative paths starting with a single `/`) or explicitly validated to match the current trusted host config (`APP_URL`).
**Prevention:** Introduce `safeRedirect()` and `isSafeUrl()` on the core `Response` object. Reject any redirect target starting with `//`, `/\\`, or `/ ` (avoiding protocol-relative or space-obfuscated bypasses), and only permit absolute URLs matching the domain configured in `APP_URL`.

## 2025-03-04 - Mitigate Brute-Force and Resource-Exhaustion DoS on Login via Session-Based Throttling
**Vulnerability:** The authentication system permitted unrestricted login attempts, allowing attackers to carry out brute-force and credential-stuffing attacks. Because BCrypt password verification is computationally expensive, large volumes of concurrent login requests also exposed the server to CPU-exhaustion Denial-of-Service (DoS) attacks.
**Learning:** To satisfy zero-dependency and zero-external-infrastructure constraints, a lightweight and self-contained rate limiter can be implemented directly on top of the framework's existing Session store. Throttling based on the client-supplied email prevents brute force on individual user accounts without introducing database schema complexity.
**Prevention:** Track failed login attempts and lockout timestamps under MD5-hashed, email-specific session keys. Block and redirect any requests that exceed 5 failed attempts within a 60-second window, bypassing heavy database queries and BCrypt hashing entirely during the lockout period.
